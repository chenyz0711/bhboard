# BHBoard · 兄弟站

一个给"兄弟们"用的纯前端互动平台：留言、联机对战、小游戏、照片墙，全部塞在一个静态站点里。

- **在线地址**：<https://bhboard.pages.dev>
- **部署方式**：GitHub → Cloudflare Pages 自动构建
- **技术栈**：原生 HTML / CSS / JavaScript（零框架、零构建步骤）+ Upstash Redis（数据）
- **代码量**：约 1 万行，17 个文件，单文件即单模块

---

## 它是怎么跑起来的

这个项目**没有自己的后端**。所有页面都是静态文件，由 Cloudflare Pages 直接托管；数据的读写全部由浏览器端 JavaScript 直连 Upstash Redis 的 REST 接口完成。

这样做的直接好处是部署极简——推代码即上线，不需要维护任何服务进程。代价是数据库凭证必须下发到客户端，因此本项目的安全模型是**"熟人站点 + 密钥准入"**，而不是真正的多租户安全边界。详见下方「安全说明」。

联机的实现方式同样朴素：**数据库当状态中转站 + 前端轮询**。A 的操作写进 `bh_room:房号`，B 轮询读到后跟进。掰手腕那类高频计数场景则用 `INCRBY` 原子累加，避免并发覆盖。

没有后台定时任务，所以过期数据采用**懒清理**：页面刷新或轮询读取时顺带检查 `updatedAt`，超过 30 分钟的房间就地删除。

## 门禁与访客模式

全站统一由 `keycheck.js` 管控，单点登录：主页登录一次，登录态写入 `localStorage`，各子页面直接读取，未登录一律重定向回主页（相对路径 `/`，换域名无需改代码）。

密钥校验顺序：

1. **黑名单**最优先——被注销者即使本地还留着登录态也会被清除并踢回主页
2. 本机已登录 → 直接放行
3. **密钥留空 → 访客模式**（见下）
4. 通用密钥 → 放行（可登任何账号）
5. 查 `bh_keys`：未使用则绑定到当前名字并放行；已绑定是自己则放行；已绑定是别人则拒绝

**访客模式**是三层防护，核心保证是"绝不落库"：

- **登录层**：密钥留空即以访客进入，账号名自动生成，本地标记 `guest: true`，登录全程不写服务器
- **写入层**：`keycheck.js` 在加载时劫持 `window.fetch`，访客身份下所有发往数据库的写操作（`set` / `del` / `incrby` / `expire` 等）直接返回 403 且请求不真正发出；读操作（`get`）照常放行
- **入口层**：首页只给访客显示本地可玩的入口（走廊瓶子赛、南外生存、公告），隐藏所有联机与写入类页面

管理员权限为双重校验：**密码正确 + 账号名是 `chenyz`**，缺一不可。

## 数据结构

所有数据存在 Upstash Redis，键名统一 `bh_` 前缀：

| 键名 | 用途 | 说明 |
|---|---|---|
| `bh_keys` | 密钥登记表 | 密钥 → `{ owner, usedAt, users: { 名字: { count, lastAt } } }`，同一密钥可多人使用、分别计数 |
| `bh_banned` | 注销黑名单 | 用户名数组，命中即无法登录 |
| `bh_members` | 持久成员表 | `{ 名字: { firstSeen, lastSeen } }`，管理页列名单用 |
| `bh_member:名字` | 在线心跳 | 值为时间戳，TTL 90 秒，过期即视为离线 |
| `bh_messages` | 论坛留言 | 全部留言数组 |
| `bh_pending` | 待处理消息 | 论坛发言的备份队列 |
| `bh_notice` | 公告内容 | 管理员在公告页编辑 |
| `bh_registry` | 对局总列表 | 开局页与管理页共用的房间索引 |
| `bh_room:房号` | 轮盘赌房间 | TTL 7 天，闲置 30 分钟懒清理 |
| `bh_room_creates` | 轮盘赌建房计数 | 按"名字 + 日期"记录，每人每天限建 10 个 |
| `bh_nfls2:房号` | 联机生存房间 | TTL 1 天，闲置 30 分钟懒清理（与轮盘赌分开） |
| `bh_nfls2_creates` | 联机生存建房计数 | 独立的每日 10 个额度 |
| `bh_photos` | 照片索引 | 含缩略图，照片墙只读这一个键 |
| `bh_photo:ID` | 单张照片 | 完整数据，点大图时才加载 |
| `bh_music` | 音乐索引 | 数组，含外链与上传曲目的元数据 |
| `bh_music:ID` | 单首上传音频 | 压缩后的 base64，播放时才加载；受 1.2MB 限制只能存短片段 |

浏览器端 `localStorage`：`bh_user`（登录态）、`bh_access_key`（记住的密钥）、`bh_admin`（管理员解锁态，sessionStorage）、`nfls_prob_unlocked`（概率显示解锁）。

### 写入方式的坑

Upstash REST 接口**只支持路径式写入**（`/set/键/值`），用 JSON Body 会返回 400。这带来两个实测约束：

- 单条数据超过约 **1.2MB 会触发 HTTP 431**，所以照片压缩目标定为 1MB 以内
- 好处是路径式写入天然支持 TTL（`/set/键/值/ex/秒数`）

照片上传走前端 Canvas 压缩：先逐步降质量，压不进目标大小再逐步缩尺寸。

## 本地运行

不需要 `npm install`，也不需要构建。静态文件直接用浏览器打开即可（推荐用本地服务器，避免 `file://` 下的路径问题）：

```bash
cd bhboard
npx serve .
# 或
python -m http.server 8080
```

要跑通联机与数据读写，需要一个可访问的 Upstash Redis 实例。凭证在 `keycheck.js` 顶部以编码形式存放，各页面通过 `window.KeyGate.credentials()` 取用，代码中不出现明文注释。

`api/` 下的两个 Vercel 服务端函数（`auth.js`、`messages.js`）是早期方案的遗留，当前纯前端模式下不参与运行，保留备用。

### 部署

推送到 GitHub，Cloudflare Pages 连接仓库后自动部署。构建命令留空，输出目录设为项目根目录——因为没有构建步骤。

## 安全说明

这是一个**熟人小站**，安全模型建立在"密钥不外泄"的前提上，请勿用于承载真实敏感数据：

- 数据库凭证下发到客户端，任何拿到页面源码的人都能直接读写数据库
- 门禁与访客拦截都在前端执行，属于"劝退"而非强制隔离；有技术能力的人可以绕过
- `api/auth.js` 以**明文存储密码**，这是早期遗留代码，当前未启用，但如果要重新启用必须先加哈希

`/docs/` 架构文档页已加登录门禁，避免数据库结构对未登录者公开。
